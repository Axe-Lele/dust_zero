# 구현 구조와 데이터 규약

최신 참조는 NEW-BUILD.md의10.15-h다. 아래 GameData 설명은 현재 프로젝트 내부 구사본의 구조이며,
신규 빌드의29개 JSON/8개 엑셀과 차이를 조사한 뒤 버전을 지정해 이행한다.

## 현재 프로젝트를 이어서 사용

루트는 clean-girls, Unity는 DustZeroUnity, 실제 코드는 Assets/DustZero/Scripts다.
가이드의 Assets/_Game와 TableDB 클래스명은 구조 예시다. 기존 GameDatabase/행 클래스/서비스를
먼저 조사하고 역할을 대응시킨다. 같은 역할의 두 번째 로더나 별도 세이브 시스템을 만들지 않는다.

- 현재 에디터6000.4.5f1 유지. URP 2D/Grid/Tilemap, uGUI+TMP 한글 폰트, Input System,
  Newtonsoft JSON, DOTween/Particle System/ObjectPool 구성에 맞춘다.
- 세로 모바일 Canvas 기준1080×1920, Safe Area 및 다른 비율 대응. 브라우저 비교 뷰포트390×844와 구분.
- 초기 가전/적 표현은 스프라이트. M6에서 가전 Spine, 대량 적은 계속 스프라이트/풀링.
- Addressables는 출시 전 원격 에셋/테이블 단계, Localization은 해외 준비,
  IAP/광고/Mobile Notifications/클라우드 저장은 출시 연동 단계로 분리한다.
  도입 예정은 설치 완료가 아니다. 서비스 연결·가격·정책은 실제 도입 때 확인한다.
- `project.yaml`의 offline/online 설정은 현재 개발 상태다. 미래 서비스 요구가 있다는 이유로 지금 온라인 완료로 바꾸지 않는다.

## 데이터

원본 엑셀→`GameData/tools/build.py`→JSON+tables.js→기존 Unity 동기화 흐름을 유지한다.
`gen_tables.py`는 초기 생성 도구이며 실행 시 엑셀 수정분을 덮어쓸 수 있다.
정기 동기화/검증 작업에서 무조건 실행하지 않는다. JSON 직접 수정으로 엑셀과 분기시키지 않는다.

| 규약 | 검증 |
| --- | --- |
| 시트명=테이블명, 1행컬럼/2행설명/3행부터데이터 | 컬럼 위치가 아닌 이름으로 읽고 필수키 검사 |
| # 시트/# 첫셀 행 제외 | 제외 규칙을 변환기와 동일하게 적용 |
| 단일행 PK id, 묶음 groupId+seq | 중복/빈 키, 중복 순번 검사. 실제 테이블별 키 예외 확인 |
| enums.json이 enum 정의 원본 | 실제 스키마를 읽어 C# enum 생성; 숫자를 별도 정의하지 않음 |
| 문구 string_ko, 참조 *Key | 누락 키/포맷 인자 검사. 한국어를 UI 코드에 흩뿌리지 않음 |
| 보상 reward_group, 비용 costItem+costCount | kind/refId/min/max/prob와 참조 그룹 검사 |
| 해금 condition id | 중복 조건 구현 대신 공통 평가기 사용 |
| map_entrance/map_tile 원본 시트→map JSON | 지상 연결/비행 경로/입구·목표/배치 금지 검증 |
| 변경은 의미 있는 diff | 행 수가 같다는 이유로 동일하다고 판정하지 않음 |

현재22개 JSON과 목표 누락6개 테이블은 BASELINE-INVENTORY.json에 기록되어 있다.
unit_star/unit_boost/attendance/guide/shop_product/pass_level 추가는 별도 스키마 변경으로 다룬다.
목표의 조각 재화/포자/난도 파라미터 등 기존 테이블 변경도 함께 필요하다.
부팅에서 참조 무결성을 검사하고 필수 테이블 누락을 빈 배열로 숨기지 않는다.
현재 방식에 맞춰 TextAsset 로드 위치를 유지하고 원격 로딩은 같은 조회 인터페이스 뒤에 연결한다.

## 로직/표현 분리

| 역할 | 책임 |
| --- | --- |
| 데이터베이스 | 전체 로드, id/group 조회, 참조 무결성 |
| SaveService | 버전/원자적 교체/백업/복구/마이그레이션 |
| Reward/Condition | 보상 지급·획득·중복 처리, 공통 해금 판정 |
| Idle/Growth/Gacha/Stage | 방치bank·수령, 비용/성장, 가중 추첨/확정, 기록/일회성 보상 |
| BattleSim/경로/유닛·적 모델 | 화면 없는 고정 틱 전투, 지상·비행·AI별 이동/저지 |
| 스킬 전략 | WantsSkill/시작/지속/종료, 실제 unit ID 집합 전체 대응 |
| BattleView/DeployInput | 모델 상태→그림/이펙트, 입력→검증된 시뮬 명령 |
| SurvivorSim | 이동/생성/격자 충돌/경험치/선택/생존 기록, 표현과 분리 |
| Shop/Pass 및 공급자 | 상품/기간/수령/권리 상태, 결제·광고의 테스트/실제 공급자 분리 |

씬 책임은 Boot(테이블·저장·방치 계산)→Lobby(패널 전환)→Battle(스테이지ID)→결과→Lobby.
대청소 진입/종료도 같은 진행 데이터와 연결하되 기존 씬 구성을 조사한 뒤 통합한다.

## 전투 틱 순서

1. 시간·전력·스폰·재배치 대기.
2. 컴퓨터/선풍기 오라와 타일 효과.
3. 가전 냉각/회복→스킬 지속/충전/자동발동→평타/스킬 틱.
4. 적 상태효과→저지 공격 또는 이동→저지 시도→누수.
5. 과열 정지, 사망 적 정리, 저지 수 갱신.
6. 승패.

고정 시간 간격(가이드 예시1/30초)과 고정 입력/랜덤 시드를 사용한다.
2배속은 같은 틱 횟수를 더 실행한다. 프레임 부하/배속에 따른 동일성은 테스트로 확인한다.
화면 없는 시뮬레이터도 동일 코어를 사용하고 별도 근사 전투 로직을 작성하지 않는다.
데미지는 시뮬 시간 기준이며 애니메이션 hit 이벤트로 다시 주지 않는다.

## 저장/외부 서비스 경계

재화·가전·조각·편성·기록·일회 보상·튜토리얼·방치bank·설정을 저장하고,
목표 기능 도입 시 출석 순번/날짜, 일일 생존 구간, 상점 제한/구매 권리, 시즌/수령 상태를 마이그레이션한다.
중복 콜백/재시작에도 동일 보상이 다시 지급되지 않도록 지급 식별자와 상태 저장 경계를 설계한다.
오래된 세이브를 버리지 않고 테스트 사본으로 이전/손상 복구를 검증한다.
시간/난수/파일시스템을 주입 가능하게 해 날짜 전환·역행·확률·실패를 재현한다.
기기 시계 방지 방식/서버 시간 도입은 미결정이다. 로컬 역행 검사만으로 조작 불가능하다고 주장하지 않는다.

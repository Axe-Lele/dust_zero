# 디자인 전수 점검 — 10.18-c 원본 대 Unity (2026-10-19)

## 0. 먼저: "1px 차이 없게"는 정의부터 해야 한다

**원본에는 고정된 픽셀 치수가 없다.** 반응형 CSS라서 같은 버튼이 390 폭 기기에서 55px,
430에서 58px, 540에서 72px로 렌더된다. 실제로 재 봤다 — 탭바 높이만 78px로 고정이고
가로 치수는 전부 뷰포트를 따라 움직인다.

그래서 비교에는 **기준 기기**가 필요하다. 이 점검은 **430×932**(현재 Unity 코드가 로비·전투에
쓰는 기준)에서 원본을 재고, Unity 캔버스 1080×1920과 비율로 맞췄다.

또 글자 래스터라이저가 다르다(Canvas2D vs TextMeshPro SDF). 같은 글꼴·같은 크기라도
자간과 가장자리 안티앨리어싱이 1~2px 다르다. **글자 획 단위의 0px 일치는 달성 불가능하다.**
아래는 그 대신 **치수·색·비율을 수치로 대조**한 결과다.

## 2. 색 — 전수 일치

원본 `:root` 커스텀 속성 24개 중 색 21개를 `UiTheme` 와 1:1 대조했다. **21/21 완전 일치.**
`--bg --ink --muted --line --card --panel --panel-2 --panel-ink --panel-muted --led --led-dim
--cool --danger --ok --heat --r --r-bg --sr --sr-bg --ssr --ssr-bg` 전부 16진수까지 같다.
나머지 3개는 글꼴 변수다. Unity 전용 색 21개(버튼 테두리·타일 색 등)는 원본에 대응이 없다.

## 3. 환산 기준이 둘로 갈려 있다 — 가장 큰 문제

`UiTheme` 에 환산 함수가 셋이다.

| 함수 | 식 | 계수 | 전제 |
|---|---|---|---|
| `Pt(x)` | x × 1080/**390** | 2.7692 | 가이드 목업이 390 폭이라는 전제 |
| `Px(x)` | x × 1080/**430** | 2.5116 | 원본 페이지가 430 폭이라는 전제 |
| `Py(y)` | y × 1920/**932** | 2.0601 | 같은 페이지, 932 높이 |

**`Pt` 와 `Px` 는 같은 가로 치수를 10.3% 다르게 환산한다.** 그런데 화면마다 쓰는 게 다르다.

| 기준 | 화면 |
|---|---|
| `Pt` 전용 (390) | **가전 상세**(81회) · **시즌 패스**(47회) · **스테이지 행**(22회) · **출석**(14회) · 패스 행 · 칩/세그먼트 |
| `Px`/`Py` (430) | 로비 · 전투 · 일러스트 뷰어 · 장비 가방 · 결과 · 덱/유닛/상점 카드 |
| 둘 혼용 | `BuildBattleUI`(Pt 4) · `BuildLobbyUI`(Pt 3) |

즉 **가전 상세와 시즌 패스는 나머지 화면보다 가로로 10.3% 크게** 그려진다.
세로는 더 벌어진다 — `Pt`(2.769) 대 `Py`(2.061)로 **34% 차이**다.

`Px`/`Py` 가 서로 다른 것 자체는 의도된 선택으로 보인다. 430:932(0.461)를 1080:1920(0.563)에
채우려면 세로를 눌러야 한다. 다만 그 대가로 **원본에서 정사각형·원이던 것이 Unity 에서
가로로 21.9% 퍼진다.** 코드에도 그 흔적이 있다 — `ProjectBuilder.cs:1003` 은
`Mathf.Min(Px(80), Py(80))` 로 한 군데만 손으로 막아 놨다.
같은 수치를 `Px`/`Py` 로 나란히 쓰는 줄이 **23곳** 있고 대부분 간격·여백이다
(`spacing = new Vector2(Px(6), Py(6))` → 15.1 × 12.4px, 정사각 간격이 아니다).

### 실측 확인
- 로비 상단 카드 좌여백: 측정 **40px** = `Px(16)` 40.2 ✓ (`Pt(16)` 이면 44.3)
- 하단 탭바 높이: 측정 **161px** = `Py(78)` 160.7 ✓ — 원본 78px(430·540 양쪽에서 고정)

로비는 430 기준으로 정확하다. 문제는 **다른 기준을 쓰는 화면들**이다.

## 4. 글자 크기 — 원본 26종 대 Unity 6종

원본 CSS 의 `font-size` 는 8.5px부터 34px까지 **26종**이고, 많이 쓰는 순서는
12.0px(56개 규칙) · 11.0(32) · 14.0(28) · 13.0(26) · 11.5(20) · 12.5(16) 이다.

Unity 는 6종이다. 430 기준으로 역산하면:

| Unity | canvas px | ≒ 원본 CSS px |
|---|---|---|
| `Display` | 69 | 27.5 |
| `Title` | 58 | 23.1 |
| `NumberL` | 47 | 18.7 |
| `Body` | 38 | **15.1** |
| `LabelSize` | 33 | 13.1 |
| `Caption` | 30 | 11.9 |

`Caption`(11.9)은 원본 12px와 맞는다. 그런데 **원본의 주력 본문이 12px인데 Unity 의
`Body` 는 15.1px 상당**이다. 본문 자리에 `Body` 를 쓴 곳은 원본보다 **약 25% 크다.**
10.5~9px 짜리 작은 라벨(원본 20개 규칙)에 대응하는 Unity 상수는 아예 없다.

## 5. 가전 상세 능력치 블록 — 디자인 자체가 다르다

원본(`.stats`):
```
display:grid; grid-template-columns:repeat(2,minmax(0,1fr)); gap:6px 14px
.stats div { display:flex; justify-content:space-between; font-size:12.5px;
             border-bottom:1px solid var(--line); padding-bottom:5px }
.stats dd  { font-family:var(--f-led); font-size:14px }
```
→ **배경 없는 2열 정의 목록.** 라벨 왼쪽(흐린 색 12.5px) · 값 오른쪽(LED 글꼴 14px),
항목마다 1px 밑줄, 칸 높이는 내용에 따라 가변.

Unity: `Pt(170)×Pt(50)` = **470.8×138.5px 고정 크기 베이지 둥근 타일**, 캡션 위 / 값 아래.

이건 1px 문제가 아니라 다른 디자인이다. 10.16-d 에서 상세 창을 탭 구조로 재설계한 흔적이라
**의도한 변경인지 확인이 필요하다.** 의도한 것이면 "원본과 다른 점"으로 기록하면 되고,
아니라면 블록 전체를 다시 그려야 한다.

## 6. 이번에 하지 않은 것

- **화면별 요소 단위 좌표 대조.** 원본 CSS 규칙 770개 · 선언 3,063개 중 수치를 가진
  것을 Unity 각 요소와 1:1로 맞춰 보는 작업은 하지 않았다. 위 3·4장이 **기준 자체의
  어긋남**을 먼저 드러냈기 때문에, 기준을 정리하기 전에 개별 좌표를 맞추면 두 번 일하게 된다.
- **리그·콘텐츠·소환·상점 상세** 등 아직 포팅 중이거나 없는 화면.
- **글자 렌더링 비교.** 래스터라이저가 달라 의미가 없다(0장).

## 7. 권하는 순서

1. **기준을 하나로 정한다.** 어느 기기 폭을 원본의 기준으로 볼지 정하고(430 권장 — 이미
   로비·전투가 그 기준이고 실측도 맞는다), `Pt` 를 쓰는 6개 빌더를 `Px`/`Py` 로 옮긴다.
   이게 가장 큰 차이를 한 번에 없앤다.
2. **`Pt` 를 삭제**해 같은 실수가 다시 나오지 않게 한다.
3. 정사각형·원이어야 하는 곳(간격 23곳 포함)에 `Mathf.Min(Px(n), Py(n))` 규칙을 세운다.
4. 글자 크기 사다리를 원본 분포(12 / 11 / 14 / 13 / 11.5 / 12.5 중심)에 맞춰 다시 짠다.
5. 그 다음에 화면별 요소 좌표를 훑는다. **순서를 바꾸면 안 된다.**

## 9. 조치 완료 (2026-10-19) — 기준 430 통일 · `Pt` 제거 · 능력치 블록 복원

### 9.1 `Pt` 를 없앴다
`UiTheme.Pt` 와 `PxPerPt` 를 **삭제**했다. 호출부 **235곳**을 축에 따라 옮겼다.

| | 처리 |
|---|---|
| `new Vector2(A,B)` 안 **113곳** | 자리로 축이 정해진다 — A는 `Px`, B는 `Py` (자동 변환) |
| 그 밖 **92곳** | 반지름·글자크기·가로는 `Px`, 높이는 `Py` (한 곳씩 판별) |
| `UiTheme` 상수 **26곳** | 아래 9.2 로 다시 정의 |
| `UiKit` 2곳 · `StageRow` 2곳 | `Px` / `Py` |

남은 `Pt` 참조 **0건**.

### 9.2 상수를 원본 실측값으로 다시 깔았다
브라우저에서 430×932 로 직접 잰 값이다(`getComputedStyle` + `getBoundingClientRect`).

| 상수 | 전(Pt) | 원본 실측 | 후 |
|---|---|---|---|
| `ButtonTall` | 177.2px | `.primary` 높이 **46** | `Py(46)` = 94.8 |
| `ButtonShort` | 138.5px | `.seg button` **33** | `Py(33)` = 68.0 |
| `ButtonCorner` | 24.9px | `.primary` radius **10** | `Px(10)` = 25.1 |
| `PanelCorner` | 36.0px | `.sheet` radius **12** | `Px(12)` = 30.1 |
| `ModalCorner` | — | `.mbox` radius **16** | `Px(16)` 신규 |
| `OverlayCorner` | — | `.ov-card` radius **14** | `Px(14)` 신규 |
| `HairLine` | 1.4px | border **1.5** | `Px(1.5)` = 3.8 |
| `ScreenPad` | 33.2px | `.modal` padding **16** | `Px(16)` = 40.2 |
| `S4…S24` | 390 목업 pt | 원본 gap 값 | `Px(4…24)` |

반지름은 전후 차이가 0.2~0.8px뿐이었다 — 원래 430에서 재서 390으로 환산해 넣은 값이었기
때문이다. **간격과 버튼 높이만 목업 포인트 그대로**여서 어긋나 있었다.

### 9.3 능력치 블록을 원본대로 되돌렸다
`Px(170)×Py(50)` 베이지 둥근 타일 4개 → 원본 `.stats` 그대로:
2열 그리드(gap 6px/14px), 줄마다 **라벨 왼쪽**(muted 12.5px) · **값 오른쪽**(LED 14px),
아래 1px 선. 배경도 고정 높이도 없다.

### 9.4 줄 높이를 따로 적으면 글자가 사라진다 — 네 곳에서 터졌다
세로가 26% 줄자 **글자 칸이 줄 높이보다 짧아져 TMP 가 아무것도 안 그렸다.**
`Py()` 로 적어 둔 높이를 전부 `UiTheme.Row(글자크기, 원하는높이)` 또는 `Line()` 으로 바꿨다.

| 곳 | 증상 |
|---|---|
| 스테이지 행 이름 | 자리 54px / 필요 57px — 행을 두 줄의 줄 높이 + `.srow` padding 9px 로 계산 |
| 상세 서브탭 | 자리 55 / 필요 57 — 원본 `.seg`(39) · `.seg button`(33) · `padding:3px` 로 |
| 레벨 줄 · 별 띠 · 비용 칩 | 각각 49/60, 54/57, 38/45 — `Row()` 로 묶음 |

### 9.5 검증
EditMode **131/131** · PlayMode **6/6** · 증거 28장 재생성.
`UiThemeTests.EveryMetricIsOnTheOriginalsOwn430x932Page` 를 새로 넣어 실측값이 바뀌면
테스트가 깨지게 했다.

### 9.6 남은 것
- **상세 창 아래 빈 공간.** 능력치가 타일에서 두 줄 목록으로 줄면서 시트 가운데가 비었다.
  원본 `.mbox` 는 내용 높이를 따라가므로 시트도 내용에 맞춰 줄여야 한다.
- **`Px` ≠ `Py` 는 그대로다.** 430:932 를 1080:1920 에 채우는 의도된 선택이지만 원본의
  정사각형·원이 가로로 21.9% 퍼진다. 같은 수치를 Px/Py 로 쓰는 줄 23곳.
- **화면별 요소 좌표 전수 대조** (6장) — 이제 기준이 하나이므로 할 수 있다.
